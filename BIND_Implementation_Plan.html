BIND Project: Master Implementation & Development Plan

1. System Architecture & Project Flow

1.1 High-Level Architecture The BIND system operates as an event-driven, serverless orchestration kernel. It strictly enforces a "Claim-Bind-Stamp" lifecycle, decoupling the reasoning (Planner) from the execution (Router/Models).

  • Presentation Layer: React single-page application integrating MapLibre GL for geospatial rendering and a reactive Docket UI.
  • API Layer: AWS API Gateway exposing RESTful endpoints.
  • Compute Kernel: AWS Lambda running a Python/FastAPI state machine.
  • Orchestration Brain: LLM A (gpt-5.6-luna via AWS Bedrock) acting exclusively as the Planner and Verifier.
  • Execution Engines (Writers):
  • GIS Tool (GeoPandas)
  • LandRecord Mock (DynamoDB/SQLite)
  • RAG AdvisoryStore (ChromaDB + Titan Embeddings)
  • Student Vision (amazon.nova-lite)
  • Teacher Vision (gpt-5.6-terra)

1.2 Step-by-Step Project Flow 1. Input: Client submits a multimodal payload (Text Request + GeoJSON bounds + Optional Image) to the /docket/open API. 2. Parse: API Gateway routes the payload to the Lambda Kernel. A deterministic gazetteer extracts the target survey number (e.g., "202/55"). 3. Plan: The Lambda Kernel invokes gpt-5.6-luna. Luna returns a structured JSON array of required Claims (e.g., GEO.PARCEL, REG.OWNER, VIS.CROP, ADV.FERTILIZER) with assigned Harm Classes. 4. Compile & Route: The deterministic Budget Compiler assigns a specific execution engine to each claim based on Harm Class and remaining budget constraints (Max $0.08 per request). 5. Execute (Parallelized): * GIS Tool fetches polygon coordinates. * LandRecord DB queries ownership records. * Student Vision analyzes the image. * Fallback Hook: If Student Vision confidence is < 0.65, the Router synchronously escalates the image to gpt-5.6-terra. 6. Verify (Bind & Stamp): All returned Exhibits are passed back to gpt-5.6-luna (The Binder). Luna executes cross-modal predicates (e.g., Does the fertilizer circular match the vision crop? Does the image GPS fall within the GIS polygon?). 7. Output: Stamped and Rejected claims are serialized into a final Docket JSON and returned to the client UI.

1.3 Integration Points * Frontend ↔ Backend: OpenAPI (Swagger) defined REST contracts via API Gateway. * Kernel ↔ AWS Bedrock: Boto3 SDK InvokeModel API calls. * Kernel ↔ S3: Boto3 get_object for image stream processing.

2. Tech Stack & AWS Infrastructure

2.1 Primary Tech Stack * Frontend: React 18, TypeScript, Vite, TailwindCSS, MapLibre GL JS, Zustand (State Management). * Backend: Python 3.11, FastAPI, Pydantic v2, Mangum (Lambda Adapter), GeoPandas, Shapely. * Database / RAG: ChromaDB (In-memory/S3 persistent) for Vector Store, SQLite/DynamoDB for Land Records. * ML Infrastructure: AWS Bedrock exclusively. No custom training frameworks. * IaC (Infrastructure as Code): AWS SAM (Serverless Application Model).

2.2 Specific AWS Resources * AWS SSO (fai-tce-team03): Identity management. All resources strictly deployed in ap-south-1 (Mumbai). * AWS S3: fai-tce-team03-datasets for raw data ingestion; fai-tce-team03-app-state for ChromaDB persistence. * AWS API Gateway: HTTP API tier for low-latency, low-cost routing. * AWS Lambda: Serverless execution of the Python FastAPI kernel. Justification: Prevents idle EC2 costs, respecting the $100 budget limit. * AWS Bedrock: Invocation layer for luna, terra, nova-lite, and titan-text-v2. * Amazon DynamoDB: Key-value store for mock land records. Justification: Zero configuration, scales to zero.

2.3 AWS Environment & Model Setup Guide 1. Authentication: All members authenticate via AWS Access Portal URL. Configure local profiles via aws configure sso. 2. Bedrock Access: Navigate to AWS Bedrock Console in ap-south-1. Go to "Model Access" and verify/request access for luna, terra, nova-lite, and titan. 3. IAM Roles: Update the provided FAI-TCE-LambdaExecutionRole to include bedrock:InvokeModel and s3:GetObject on the fai-tce-team03-* resources. 4. SAM Initialization: Run sam init using a Python 3.11 template. Define the API Gateway and Lambda functions within template.yaml.

3. Data & Model Pipeline

3.1 Strict Dataset Requirements * Raw Data Location: All Task 2 (Land Documents) and Task 4 (Crop Images) files currently on OneDrive must be uploaded directly to s3://fai-tce-team03-datasets/. * Data Formatting: * Images: Must be .jpg or .png. Maximum size 4MB per image (Lambda payload limits). * Cadastral Maps: Must be converted to valid GeoJSON FeatureCollections. * Advisory Documents: Must be extracted from PDF to markdown/text chunks before vectorization.

3.2 Inter-Task Dependencies * GIS → Vision: The Vision model cannot be accepted as fact unless the GIS point-in-polygon check confirms the image GPS metadata falls within the target GeoJSON boundaries. * Vision → RAG: The Advisory RAG query is blocked until the Vision model confirms the Crop Type and Growth Stage. RAG filters must use these outputs as hard WHERE clauses.

3.3 Model Setup & Deployment Strategy * No Model Training: BIND is an inference-only orchestration engine. * Prompt Engineering: Store all LLM system prompts in a centralized /prompts configuration directory in the backend repository. * RAG Pipeline (Titan Embeddings): 1. Script pulls Advisory PDFs from S3. 2. Python chunks text by paragraphs. 3. Boto3 invokes Titan Text Embeddings. 4. Vectors are loaded into ChromaDB, mapped with metadata tags (Crop, Zone, Stage).
